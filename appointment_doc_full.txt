Purpose
This document describes the student appointment API added to the existing Averroes mobile API. It is intended for the mobile app developer implementing appointment booking, appointment history, schedule updates, cancellation, and unread/update indicators in the student app.
Integration note: The attached update ZIP does not include the existing api/student-api-common.php file. Therefore, the mobile app must continue using the same authentication mechanism, login response, request headers/cookies/token handling, and outer JSON success/error envelope already used by the current student mobile API. This document does not invent a new Bearer-token format.

2. Appointment Workflow
Student loads eligible recipients and appointment-purpose options.
Student submits an appointment request. New requests start with status requested.
Teacher/Principal/Vice Principal or authorized school staff schedules, completes, or declines the request from the ERP portal.
When the school updates the appointment, the API can return has_update = true until the student marks the update as read.
The student may cancel an appointment while it is requested or scheduled, provided a scheduled appointment has not already started.

5. Endpoint Details
GET  /api/student/appointment-recipients
Returns employees currently eligible to receive student appointments and the valid appointment-purpose values.
Authentication: Required (same student authentication as the existing API).
Request parameters: None.
Data payload shape:{  "recipients": [    {      "employee_id": 25,      "employee_uid": "EMP0025",      "name": "Example Teacher",      "designation": "Senior Teacher",      "department": {        "id": 4,        "name": "Academic"      }    }  ],  "purposes": [    {"value": "academic", "label": "Academic Discussion"},    {"value": "student_welfare", "label": "Student Welfare"}  ]}
Recipient eligibility is generated from active employees who are Academic staff or whose designation contains teacher, principal, or head, and who can be matched to an active ERP user account.

POST  /api/student/appointments/{id}/read
Marks the latest appointment notification/update as seen by the student.
Request body: none required.
Successful data payload:{  "appointment_id": 123,  "marked_read": true}
Call this after the student opens/views an appointment update. The appointment object’s has_update flag is calculated from student_notified_at versus student_seen_at.

9. Developer Implementation Notes
Do not hard-code recipient IDs. Always load them from GET /api/student/appointment-recipients.
Do not hard-code display labels if avoidable; the API already returns purpose_label, status_label, and meeting_mode_label.
Use the server as the source of truth for date and cancellation validation.
Times in appointment payloads are returned as HH:MM when present.
The generated appointment number format is APT-YYYYMM-###### based on the database appointment ID.
All appointment list/detail operations are scoped to the authenticated student; the app should never send a student_id to access another student’s appointment.
The recipient list is limited to active eligible academic/leadership staff with an active matched ERP user, so a staff member may not appear until their employee and user records are correctly linked.
